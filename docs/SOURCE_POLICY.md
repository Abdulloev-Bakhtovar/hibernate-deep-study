# Политика версий и источников

## Зафиксированная версия

- Hibernate ORM: `7.4.17.Final`.
- Jakarta Persistence: `3.2` (версия, с которой совместима ветка Hibernate ORM 7.4).
- Java: `17`.
- PostgreSQL: используется уже имеющееся локальное учебное окружение пользователя; версию сервера записать в `state/ENVIRONMENT.md`, когда она будет проверена.

На 2026-11-23 официальный сайт Hibernate помечает 7.4.17.Final (2026-11-19) как latest stable, а 8.0.0.CR1 (2026-11-12) как development. Ветка 7.4 совместима с Java 17, 21, 25 и 26. Поэтому для курса выбран стабильный 7.4.17.Final, а не 8.0 CR.

## Иерархия источников

1. Исходный код Hibernate ORM на GitHub, **точный tag `7.4.17` / соответствующий релизный tag**. В URL/ответе агента явно указывать tag, файл, класс и метод.
2. Официальная документация Hibernate 7.4: https://hibernate.org/orm/documentation/7.4/
3. Официальный User Guide: https://docs.hibernate.org/stable/orm/userguide/html_single/
4. Jakarta Persistence 3.2 specification/API — для стандартного контракта.
5. Блоги и сторонние материалы — только для дополнительного объяснения, не вместо первоисточника.

## Source trace format

Когда объясняешь внутреннюю реализацию, укажи:

- внешний API, с которого стартует действие;
- ключевой внутренний класс/интерфейс;
- важные методы и последовательность вызовов;
- структуры состояния/данных;
- переход к JDBC и SQL, если применимо;
- конкретные файлы исходников и ссылку на версию;
- что является стабильным API, а что внутренним implementation detail.

Не выдумывать названия классов/методов по памяти. Если исходник недоступен в текущей среде, честно отметить, что цепочка требует проверки.

## Обновление версии

Не менять версию посреди темы. Предложить обновление только если есть веская причина (уязвимость, несовместимость, завершение поддержки, критически нужная возможность). Записать решение, дату, старую/новую версию и влияние на уже пройденные темы в `state/DECISIONS.md`.
